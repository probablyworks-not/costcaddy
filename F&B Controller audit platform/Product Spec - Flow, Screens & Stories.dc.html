F&B Controller — Flow, Screens & User Stories

Single source of truth for development, to be read alongside the designs: Super Admin Flow, Auditor Flow — Mobile / Laptop, Template Builder, Audit report v4. Where this document and a design disagree, the design wins on layout and this document wins on behaviour.

1 · The three roles

Super Admin · laptop
Creates restaurants, auditor logins and templates. Assigns an audit. Reviews what came back and publishes the report.
Auditor · phone or laptop
Signs in, opens the audit assigned to them, types the metrics, marks every checklist point with a remark and photos, submits once.
Outlet · reader only
Receives the published report as a link. No login in this build.

2 · The whole journey, in order

Setup, once. Super admin signs in → adds a restaurant → adds auditors and gives each a password → builds a template (metrics + department checklists).
Every audit. Opens the restaurant → New audit → picks the template and the auditor → the audit is created and appears in that auditor's app.
In the outlet. Auditor signs in → opens the audit → Metrics tab: types the figures, totals calculate themselves → Checklist tab: marks every point Pass / Fail / N-A with a remark and photos → Submit.
Back at the desk. Super admin opens the submission in the review queue → reads it as captured → attaches the operational reports → Generate report → checks and edits the findings → Publish.
Out. Report v4 is shared as a link, printed or exported. Corrections are published as a new version.
Scheduling, due dates and chasing happen offline between the firm and the outlet. The product only records who is doing which audit.

4 · Screens, and what each one does

One box per screen: what is on it, what the user can do, and what must not happen. Screen IDs are stable — quote them in tickets.
4.1 · Super admin screens
SA-1Admin sign-in
On screen: email, password, "keep me signed in", sign-in button.
  • Signing in lands on Restaurants.
  • A wrong password shows one inline message and keeps the typed email.
  • No "forgot password" — passwords are handled by the admin inside the product.
SA-2Restaurants (home)
On screen: left nav (Restaurants · Auditors · Templates), a list of restaurants with name and city, and an "Add restaurant" button.
  • "Add restaurant" opens a small inline panel: name (required) and city. Save adds the row straight away; cancel keeps nothing.
  • Clicking a restaurant opens its detail screen (SA-3).
  • Empty state invites adding the first restaurant instead of showing an empty table.
SA-3Restaurant detail — Audits & Reports
On screen: restaurant name, a back link, two tabs — Audits and Reports — and a "New audit" button.
  • Audits tab lists audits in three groups: active (with the auditor's name and a shareable link), submitted and awaiting review (each row has a Review action), and audit history.
  • Reports tab lists published reports grouped by month; a row opens the report document.
  • Each row goes straight to the one place that makes sense for its state — the admin never has to work out where to click.
SA-4New audit panel
On screen: an inline panel on the Audits tab — audit name, the restaurant (already filled in), a choice of "use an existing template" or "build a new one", the template picker, and the auditor picker.
  • Choosing "build a new one" jumps to the Template Builder and comes back here with the new template already selected.
  • Create makes the audit and it appears in that auditor's app. No due date is asked for.
  • The audit takes a copy of the template as it is today, so editing the template later never changes an audit already running.
SA-5Auditors
On screen: "Add or remove auditors, issue passwords, control outlet access". A list of auditors — name, email, phone, status, outlets — and an "Add Auditor" button. A row expands in place.
  • Add Auditor asks for full name, work email (this is the login ID), phone, which outlets they cover, and a password the admin types or generates. Validation, one message at a time: name required, email must be valid, email must not already exist, password must be set.
  • Inside the expanded row: the current password is shown masked with Show / Hide and Copy; below it a field to type a new password and save. Saving replaces the password immediately and the row reflects it.
  • Also in the row: change outlet access, suspend or reactivate, end all sessions, and remove (asks to confirm).
  • Removing an auditor never deletes their submitted audits — those keep their name.
SA-6Templates library
On screen: "Checklist Templates — reusable across restaurants", a list of templates, and "New Template".
  • Each row shows the template name and an "Edit template" action that opens the builder (SA-7).
  • "New Template" opens an empty builder.
SA-7Template Builder
The most important setup screen. Header reads "Metrics the auditor enters, then department-wise checklist points". Top of the page: template name and an optional description. Below that, two parts.
Part 1 · Metrics — the numbers the auditor will type
Metrics live inside categories. Each category is a card with an icon, a name, a one-line description, a metric count and its own "Add metric to <category>" button. The shipped set of categories is Volume, Sales, Discounts, Taxes and Costs — but the admin can add, rename and delete categories freely.
  • A metric row = a name field + a type dropdown + a delete icon. Types: Currency (₹ / $), Number, Count / Pax, Percentage (%), Calculated / Auto-sum.
  • Calculated rows are shown greyed inside the category with a badge (CALCULATED, RECONCILED SUB-TOTAL) and the note "Auto-sum · no input" — the auditor never types these. Example: Volume has No of Pax as input and Total No Of Pax as calculated; Sales has Food / Liquor / Beverage as inputs and Net Sales at Restaurant as the reconciled sub-total.
  • Deleting a metric removes just that row. Deleting a category removes it with its metrics and asks once.
  • A category can hold sub-groups (for example a cost split by kitchen and bar); a sub-group has its own name, metrics and its own calculated total.
  • "Add category" sits at the bottom of Part 1 as a dashed full-width button.
Part 2 · Department-wise checklist points
One card per department, numbered in order. Each card header has the department name (editable in place), a checkpoint count, an "Add point" action and a delete icon.
  • A checkpoint row = an auto-generated reference code + the question or inspection check + a delete icon. The code comes from the department prefix and the row position, e.g. SEC-01, KIT-03 — it renumbers if rows are removed.
  • The point text is the exact question the auditor reads in the field. An optional description line can be added underneath as guidance.
  • Order on this screen is the order the auditor sees, and the order the report prints.
  • "Add department" sits at the bottom as a dashed full-width button.
  • Everything on this screen edits in place — no separate dialogs, no separate pages.
  • Save template returns to the library, or back to the New audit panel if the builder was opened from there.
  • The builder has preview tabs showing the same template as the super admin sees it and as the auditor's entry form, so the admin can check their work before saving.
SA-8Review a submitted audit
On screen: the submission exactly as the auditor left it — the metrics they entered, every checkpoint with its status, their remark word for word, and their photos. Plus a panel for attaching the operational reports (POS, purchase, payroll exports) and a Generate report button.
  • The admin can correct a status or a remark here, and can open any photo full size.
  • Operational report rows show what the file covers and whether it was read successfully; a section with no data is marked "needs data" rather than left blank.
  • Generate report turns each Fail and Observation into a finding with a reference ID, category, severity, operational impact, corrective action and owner, and compiles the financial sections from the metrics. The admin can edit any of it afterwards.
  • Publishing stamps a version and a date. A correction after publishing creates the next version with a revision note; earlier versions stay available.
4.2 · Auditor screens (phone, same on laptop)
AU-1Auditor sign-in
On screen: email, password, Log In.
  • They use the email and password the super admin issued. Nothing to set up, no password change step.
  • The session stays signed in — a phone restart or a dead zone never signs them out mid-audit.
AU-2My audits
On screen: the audits assigned to them — restaurant, template name, progress — and a "Recently submitted" section below.
  • Tapping a card opens the audit. Tapping a recently submitted one opens it read-only.
  • Newest first. Nothing about dates or being late.
  • Empty state: "No audits assigned".
AU-3Conduct audit — step 1, Metrics
On screen: "1 · Enter today's figures — totals marked calculated fill in automatically". The categories from the template, in order, each with its metric rows: label, unit, and a right-aligned number field.
  • Numeric keypad. Calculated rows are greyed and show their running value — never typed.
  • Each figure updates the totals as it is entered, so a mistyped number is obvious on the spot.
  • Everything saves as it is typed; leaving the screen loses nothing.
AU-4Conduct audit — step 2, Department checklist
On screen: "2 · Department checklist — mark each checkpoint and add the observation for the report". One collapsible card per department showing "n / m marked". Inside, each checkpoint row shows its reference code and question.
  • Tapping a row opens it. Buttons: Pass, Fail, Observation, N/A — one choice, at least 44px tall.
  • Below the buttons: a remark box, and photo actions (camera, gallery, paste screenshot on laptop). Several photos per point, each removable.
  • Fail and Observation need a remark; N/A needs a reason picked from a short list. Pass can be left bare.
  • The collapsed row then shows the status and the start of the remark, so progress is readable at a glance.
  • Any answer can be changed until submit. Changing a status never deletes photos already taken.
AU-5Submit
On screen: a Submit button pinned to the bottom of the audit.
  • Disabled until every checkpoint is marked and every required remark, reason and photo is there. The button says what is missing, in a count.
  • Tapping the notice jumps to the first point that needs attention.
  • Submitting is confirmed once, then the audit becomes read-only for the auditor and moves to the admin's review queue.
  • If the phone is offline the submission is held and sent by itself — nothing is re-entered.
AU-6My submitted audit
On screen: the audit as submitted, read-only, and once published a link to the report.
  • The auditor can read severity and corrective actions but cannot change them — judgement is the reviewer's job.
4.3 · Audit report v4
RP-1What the report is made of
Four sections, in this order. Nothing in the report is typed twice — every number and sentence traces back to something captured earlier.
  • Section 1 — key financial and unit economic metrics. Built from the auditor's metrics plus the attached operational reports. Per-cover figures divide by the pax the auditor entered.
  • Section 1B — costing and cost as a percentage of sales. Cost lines against their revenue group, so kitchen cost sits against kitchen sales.
  • Section 2 — department checklists. Every checkpoint with its reference code and status, grouped by department in template order. N/A points are shown separately and left out of the compliance percentages.
  • Section 3 — findings register. One row per Fail and Observation: reference ID, core category, the finding in the auditor's words, risk severity, operational impact, corrective action and owner.
RP-2How it behaves
  • Before publishing, the admin can edit any severity, figure or sentence, and hide a row that does not belong.
  • A section with no data says so plainly instead of showing a zero.
  • Prints and exports to PDF and XLSX with no extra setup; the on-screen and printed layouts match.
  • Once published it is frozen. A correction is published as v2 with a revision note.

5 · User stories

Each story names the screen it lives on. "Done when" is the acceptance test.
Super admin
S-1 · Add a restaurant SA-2
So that audits can be run under it.
Done when a name and city added inline appear in the list immediately, and an empty name is refused.
S-2 · Create an auditor login SA-5
So that a new joiner can work the same day.
Done when name, email, phone, outlets and a password create an account; a duplicate email is refused with one clear message; the row appears straight away.
S-3 · See and change an auditor's password SA-5
So that I can read it back to someone locked out, without a support queue.
Done when the current password is masked by default, Show reveals it, Copy copies it, and saving a new one replaces it and shows the new value.
S-4 · Control who can audit what SA-5
So that the assignment picker offers the right people.
Done when outlet access, suspend, reactivate and remove all work from the expanded row, and removing an auditor leaves their submitted audits intact.
S-5 · Build the metric set SA-7
So that the auditor is asked for exactly the numbers this client's report needs.
Done when I can add a category, add metrics to it, set each metric's type, mark a row as calculated, reorder, and delete — all in place, and the auditor's form changes to match.
S-6 · Build the department checklists SA-7
So that the walk follows the departments in the right order.
Done when I can add a department, rename it, add points with their question and guidance, delete a point, and delete a department — and reference codes renumber themselves.
S-7 · Assign an audit SA-4
So that the right person walks into the right outlet with the right checklist.
Done when picking a template and an auditor creates the audit, it appears in that auditor's list, and it holds a copy of the template so later edits don't disturb it.
S-8 · Build a template mid-assignment SA-4 → SA-7
So that a first audit for a new client isn't a two-trip job.
Done when choosing "build a new one" opens the builder and saving returns to the New audit panel with that template selected.
S-9 · Read a submission as captured SA-8
So that I judge the outlet, not the auditor's typing.
Done when statuses, remarks and photos appear exactly as submitted, photos open full size, and I can correct a status or remark.
S-10 · Attach the operational reports SA-8
So that the financial sections are built on the client's own exports.
Done when a file can be attached and replaced, each shows what it covers and whether it read successfully, and a section with no data is marked "needs data" rather than left blank.
S-11 · Generate the report SA-8 → RP-1
So that a page of findings takes a button, not an evening.
Done when every Fail and Observation becomes a finding with reference ID, category, severity, impact, corrective action and owner, and the financial sections fill from the metrics.
S-12 · Correct and publish RP-2
So that my name goes on something I actually agree with.
Done when any generated field can be edited or hidden before publishing, publishing stamps a version and date, the report becomes read-only, and a correction publishes as v2 with a revision note.
Auditor
A-1 · Sign in and stay in AU-1
So that a dead zone or a restart never costs me my place.
Done when the issued email and password sign me straight in, a wrong password keeps my email and shows one message, and I am never signed out mid-audit.
A-2 · See what is mine AU-2
So that I know where to go next without calling the office.
Done when each card shows restaurant, template and progress, newest first, with recently submitted audits below and a clear empty state.
A-3 · Type the figures fast AU-3
So that a page of numbers takes minutes.
Done when a numeric keypad appears, each field shows its unit, and letters are refused without a dialog.
A-4 · Never type a total AU-3
So that I catch a mistyped figure while I am still in the outlet.
Done when calculated rows are read-only, greyed, badged, and update as I type the inputs they depend on.
A-5 · Work department by department AU-4
So that I finish the kitchen before I walk to the store.
Done when departments collapse and expand, each header shows how many points are marked, and the order matches the template.
A-6 · Mark a point in one tap AU-4
So that forty checkpoints do not become forty forms.
Done when a row expands in place, Pass / Fail / Observation / N/A are one exclusive choice at 44px, and the collapsed row then shows the status and the start of my remark.
A-7 · Explain and prove it AU-4
So that the report reads my words, not a guess at what a red mark meant.
Done when I can write a remark of any length and attach several photos per point, each removable, and my wording reaches the report unedited.
A-8 · Say why something doesn't apply AU-4
So that a bar check in an outlet with no bar isn't counted against it.
Done when N/A requires a reason, and N/A points are excluded from compliance percentages and listed separately in the report.
A-9 · Leave and come back AU-3 · AU-4
So that a phone call or a flat battery costs me nothing.
Done when every entry saves as it is made, everything is restored on reopening even offline, and Back never asks me to discard anything.
A-10 · Be stopped from submitting half a job AU-5
So that nothing comes back to me after I have left the outlet.
Done when Submit is disabled with a count of what is missing, and tapping it jumps to the first point needing attention.
A-11 · Submit once, clearly AU-5
So that I know the visit is closed and what I handed over.
Done when a confirmation names the outlet and the counts, the audit then goes read-only, and an offline submission sends itself later without re-entry.
A-12 · Work at a laptop too AU-3 · AU-4
So that typing up emailed exports isn't a phone chore.
Done when the same flow and data work at desktop width, with wider rows, a photo grid, drag-and-drop and paste.

6 · Rules that hold everywhere

  • The audit owns its own copy of the template. Editing a template never changes an audit that is already running or already submitted.
  • The auditor records fact; the reviewer judges. Severity, operational impact, corrective action and owner are never set in the field.
  • Remarks are quoted, not rewritten. The auditor's words reach the report as they were typed.
  • Nothing is lost. Every entry saves as it is made and survives being offline. Submitted work is read-only for the auditor; published reports are frozen for everyone.
  • N/A is not a failure and not a blank. It needs a reason, is excluded from percentages and is listed separately.
  • One message at a time. Validation names the first problem and focuses it, rather than listing everything at once.
  • Calculated is never typed. Any figure the system can derive is read-only wherever it appears.
Not in this build
Outlet-side accounts and task assignment — outlet users, corrective actions pushed to named owners, findings closed from the outlet side. A placeholder screen holds its place in the nav. Also out: due dates, reminders and overdue tracking (handled offline), severity set in the field, recurring audit schedules, and in-app chat.
